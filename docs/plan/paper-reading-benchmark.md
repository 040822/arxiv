  ## Benchmark 设计

  ### 题库与版本

  - 版本命名使用 pprb-<subset>-YYYY.MM.DD-rN，例如 pprb-pilot-2026.08.04-r1。
  - 状态为 draft → review → frozen → retired；冻结后不可原地修改。
  - 论文、全文、Prompt、问题、参考答案、证据或 rubric 有任何变化，都通过克隆产生新版本。
  - 裁判模型或裁判 Prompt 使用独立的 scoring_revision；重新评分保存为新评分版本，不覆盖旧结果。
  - 冻结内容包括论文元数据快照、完整提取文本、PDF/文本哈希、生产 Prompt 快照和题库校验和。删除原业务论文不能破坏已有 benchmark。
  - 创建草稿时默认复制当前 deep_reading 和 paper_chat Prompt；后续生产 Prompt 修改不会影响旧题库。

  ### 两条独立评测轨道

  1. 深度阅读轨
      - 每篇论文调用一次冻结的生产深度阅读 Prompt。
      - 默认对应当前 Q1–Q6，分别评估问题与动机、相关研究、方法、实验、局限/延伸和整体总结。
      - 自动解析每个 Q 的回答；缺失 Q 直接记该题 0 分。
      - 保留现有的一次截断续写行为，并单独报告续写率、额外 token 和费用。

  2. 论文交流轨
      - 每篇论文采用一个固定三轮脚本，连续保留该候选模型自己的历史回答。
      - 第一轮测试准确解释，第二轮测试基于前文的跨章节追问，第三轮测试错误前提、边界条件、纠错或局限。
      - 三轮问题由出题模型生成、用户逐题确认，冻结后所有候选使用相同脚本。
      - 分数包含事实正确性、上下文一致性、是否直接回答、认识边界和交流帮助度。

  两个轨道分别排名，不合成任意权重的总榜。

  ### 半自动题库生产

  - 每篇论文约使用两次出题调用：一次生成深度阅读参考答案/rubric，一次生成三轮交流脚本。
  - 每个题目保存参考答案、逐项评分标准、权重、关键错误条件和必须能在冻结全文中精确找到的证据片段。
  - 系统自动拒绝证据不存在、只依赖图片、参考答案与证据矛盾或缺少评分标准的题目。
  - 用户必须逐题接受、编辑或驳回；未全部通过人工确认的题库不能冻结。
  - v1 不评测图片、扫描件和只能从图表视觉内容获取的信息；全文提取失败时阻止冻结，不回退摘要生成正式分数。
  - 私有问题减少题目泄漏，但论文可能已存在于模型训练数据中，因此正式题目优先要求跨章节综合、具体实验细节和错误前提识别，避免仅凭摘要或常识作答。

  ### 评分与裁判

  - rubric 采用叶子条件，裁判只能输出 met=1、partial=0.5、unmet=0，避免宽泛的整体 1–10 分。
  - 单题分数为加权条件平均；严重捏造论文方法、数字或实验结论时，该题最高限制为 60 分。
  - 先按题汇总到论文，再对论文做等权宏平均，避免某篇题目多而主导总分。
  - 主裁判评分全部输出；第二个不同模型家族的裁判复核：
      - 至少每个轨道、每个候选抽取 10%；
      - 主裁判低置信度；
      - 发现严重幻觉；
      - 规则检查与裁判冲突；
      - 主裁判与候选属于同一模型家族。

  - 两个裁判不一致时进入人工确认；人工结果优先级最高，且不覆盖原始裁判记录。
  - pilot 用人工结果计算裁判的逐条件一致率和分数误差。未经校准的裁判结果必须显示“未校准”警告。
  - 默认每个候选运行 1 次；界面保留 1–5 次配置，便于后续手动改为 3 次。
  - 1 篇 pilot 不显示正式排名或置信区间；达到 8 篇后按论文聚类 bootstrap 给出 95% 区间。区间重叠的模型标记为“当前样本无法区分”。

  ### 模型、思考强度与成本

  - 候选配置复用现有供应商凭据和 build_chat_completion_kwargs()，每个候选保存 provider、model、思考开关、请求强度、实际映射参数、输出上限和配置哈希，不保存 API Key。
  - 同一模型的不同思考强度视为不同候选，但只有供应商真正发送了不同参数时才允许比较。
  - 明确记录当前协议限制：
      - OpenAI reasoning 通常能区分 low/medium/high；
      - Qwen 类协议可映射为不同 thinking budget；
      - DeepSeek legacy reasoner 不接受可比较的强度参数；
      - 不同供应商的“high”不代表相同推理预算。

  - 若两个强度最终生成相同的线上请求参数，界面应提示“该供应商不支持此区分”，避免产生虚假的强度对比。
  - 默认使用各轨道统一的输出上限；若用户允许候选使用不同上限，报告必须标记为“非等预算比较”。
  - 报告分别展示质量、输入/输出/缓存 token、延迟、截断与续写次数。价格不写入供应商配置，而是在运行时提供可选价格快照。
  - 预估调用量：
      - 被测调用：论文数 × (1 次深度阅读 + 3 次交流) × 重复次数；
      - 1 篇 pilot 为每候选约 4 次，8 篇正式集为约 32 次；
      - 裁判按“每篇论文、每个轨道”批量评分，基础约 2 次裁判调用/论文/候选，再加复核。

  - 发起运行前展示正常与最坏调用数、token 上限和估算费用，并允许设置硬预算；超预算不得启动。
  - 完全相同的题库、Prompt 和候选配置可复用已保存回答；更换裁判只重新评分，不重复调用候选模型。

  ## 后续实现蓝图

  - 建立一个 source/benchmark/ 深模块，其外部 interface 只暴露创建草稿、生成题库、冻结、发起/恢复运行和生成报告；模型调用、版本校验、评分聚合与重试隐藏在模块内部。
  - 增加 benchmark_author、benchmark_judge 和 benchmark_judge_review 三个任务路由；被测候选仍从 deep_reading/paper_chat 路由草稿解析。
  - 通过下一版连续数据库迁移保存：
      - 题库、冻结论文全文与 Prompt 快照；
      - 人工审核后的 cases、证据和 rubric；
      - 运行、候选配置、原始响应和 token/延迟；
      - 主裁判、复核裁判和人工覆盖记录。

  - 新增受管理员认证保护的 /benchmark Web 管理页，提供“选论文 → 自动出题 → 逐题审核 → 冻结 → 选模型/强度 → 预算确认 → 运行 → 报告”流程。
  - 运行任务异步、持久化且可恢复；网络、429、5xx 可重试两次，认证或网络失败不计模型 0 分。上下文超限、内容截断、格式错误属于候选配置/能力失败并进入成绩。
  - 保存 runner 版本、代码提交、Prompt 哈希和模型别名；供应商若使用可漂移的模型别名，报告提示历史纵向比较限制。

  ## 测试与验收

  - 文档审核：术语、版本规则、公式、公开 benchmark 链接和限制说明一致；docs/README.md 链接有效。
  - 后续实现时用临时 SQLite 和假模型 adapter 完成一条完整集成测试：选择 1 篇论文、生成并审核 6 个深度阅读项目与 3 轮交流、冻结、运行两个候选、复核裁判并生成分榜。
  - 覆盖冻结后不可编辑、克隆新版本、证据匹配、缺题计零、严重幻觉限制、思考参数去重、预算拦截、中断恢复、只重判不重跑、敏感凭据不落库等回归测试。
  - pilot 验收标准：每候选默认 4 次被测调用；报告包含两张独立榜单、逐论文/逐题明细、裁判状态、token、延迟与版本哈希，并明确显示“单篇 pilot，不构成可靠模型排名”。

  ## 明确边界

  - v1 不做多模态图表理解、跨论文检索、公开排行榜或通用学术能力声明。
  - 分数只代表指定论文、冻结 Prompt、当前文本管线和候选参数下的实际表现。
  - LLM 裁判只能降低人工工作量，不能替代人工审题和抽样校准。
  - 当前文档阶段不修改代码、数据库、设置文件或生产 Prompt；真正实施时再同步更新架构、开发者、API、用户、Agent 与变更日志文档。
