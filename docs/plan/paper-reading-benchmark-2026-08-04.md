# 私有论文阅读 Benchmark 设计与实施计划

**计划版本:** 2026.08.04-r1  
**状态:** v7 已实现（pilot 已跑通：FLEX-π 单篇、双候选、双轨分榜；分支 feature/paper-benchmark）
**用途:** 私人模型选型，不公开发布，不产生公共 leaderboard

## 1. 结论摘要

本项目应建设一个面向实际论文阅读流程的私有 benchmark，而不是直接套用某个公开题库。

首版采用以下固定决策：

- 评测对象是端到端阅读流程：冻结论文全文、Prompt、消息顺序和模型路由调用方式。
- 首版只做文本轨，不把图片、扫描件和只能从视觉图表读取的信息纳入正式分数。
- 题库从数据库中由用户指定论文组成；先用 1 篇论文验证流程，正式比较建议至少 8 篇。
- 深度阅读和论文交流分开排名，不合成一个带主观权重的总分。
- 题目、参考答案、证据片段和评分 rubric 由模型辅助生成，但必须逐题人工确认后才能冻结。
- 默认每个候选运行 1 次；运行界面保留 1–5 次配置，后续可将决赛候选改为 3 次。
- 主裁判评分全部输出，第二裁判只处理固定抽样、低置信度、严重幻觉和模型家族冲突样本。
- 题库冻结后，论文、全文、Prompt、题目和 rubric 都不可原地修改；修改必须创建新版本。

首个 pilot 只回答“评测管线是否可用”，不能根据 1 篇论文给出可靠的模型排名。

## 2. 公开 Benchmark 调研

目前没有公开 benchmark 同时满足以下要求：从本项目数据库任意选论文、复用本项目供应商、冻结生产 Prompt、覆盖多轮论文交流、支持私人版本化。因此公开 benchmark 只作为设计参考。

当前实现采用 schema v7：候选运行由单 worker 后台队列执行并可恢复；响应、重试、跨运行复用、
裁判评分版本和题目编辑审计均持久化。新运行固定保存 `RUNNER_VERSION=pprb-runner-v7`；历史
空版本保持为空，不在迁移时伪造回填。

| Benchmark | 可借鉴内容 | 与本项目的差异 |
|---|---|---|
| [ResearchQA](https://arxiv.org/html/2607.11074v1) | 6,211 个单篇论文问题、494 篇论文；包含 lookup、comprehension、multi-hop、adversarial，并把引文验证与 LLM 裁判分开 | 题目、答案和证据主要由同一模型生成，缺少分层人工验证；以单轮为主 |
| [QASPER](https://aclanthology.org/2021.naacl-main.365/) | 5,049 个问题、1,585 篇 NLP 论文；问题、答案和支撑证据由不同标注者提供 | 仅 NLP、单轮，不能直接使用数据库中的任意论文 |
| [ELAIPBench](https://arxiv.org/abs/2510.10549) | 专家编写的 AI 论文推理题，适合参考难度分层；研究还观察到思考模式不一定提升正确率 | 主要是选择题，不等价于深度阅读和自由交流 |
| [CURIE](https://research.google/pubs/curie-evaluating-llms-on-multitask-long-context-scientific-understanding-and-reasoning/) | 长上下文、跨章节推理和科学工作流任务分解 | 学科和任务固定，不支持用户自选论文 |
| [ScholarQABench](https://www.nature.com/articles/s41586-025-10072-4) | 专家 rubric、长答案和文献综合自动评估 | 重点是多篇论文检索与综述，并明确不覆盖动态多轮问答 |
| [PaperBench](https://openai.com/index/paperbench/) | 用分层 rubric 将复杂论文任务拆成可评分叶子条件，并单独校准 LLM 裁判 | 评测论文复现，成本和任务范围远超本项目 |

公开方案的共同教训是：单一总体分数容易掩盖证据遗漏、幻觉、跨章节失败和裁判偏置。私人 benchmark 应优先保留逐论文、逐题、逐条件明细。

## 3. Benchmark 范围与不测内容

### 3.1 v1 测试轨道

#### 深度阅读轨

- 每篇论文调用一次冻结的深度阅读 Prompt。
- 默认沿用当前生产 Prompt 的 Q1–Q6：问题与动机、相关研究、方法、实验、局限/延伸、整体总结。
- Prompt 创建题库草稿时复制为不可变快照；以后生产 Prompt 改动不会影响旧题库。
- 评分关注论文事实、方法解释、实验细节、证据覆盖、局限边界和是否把推测说成论文结论。
- 保留现有深度阅读的截断续写机制，并记录续写次数、额外 token 和最终完成状态。

#### 论文交流轨

- 每篇论文使用一个固定三轮对话脚本。
- 第一轮测试准确解释；第二轮测试基于前文的跨章节追问；第三轮测试错误前提、纠错、适用边界或局限。
- 三轮共享该候选模型自己的历史消息，评估上下文一致性和交流帮助度。
- 三轮脚本由出题模型生成，用户逐题确认后冻结。

### 3.2 v1 明确不测

- 图像、流程图、截图、扫描件和只能从视觉表格读取的内容。
- 跨论文检索、文献综述和开放网络搜索。
- 模型写代码复现实验。
- 公开 leaderboard、跨用户比较或对外发布题目。
- 把单篇 pilot 的结果解释为普遍的模型能力排名。

PDF 全文提取失败、正文为空或关键证据只存在于未提取的图表时，题库不能冻结；不能悄悄回退到摘要后继续生成正式分数。

## 4. 题库构建流程

    选择数据库论文
      → 预检 PDF、全文、哈希和上下文长度
      → 创建 draft，复制生产 Prompt 快照
      → 出题模型生成参考答案、证据和 rubric
      → 自动验证证据能在冻结全文中找到
      → 用户逐题确认/编辑/驳回
      → 冻结为版本化 subset
      → 选择候选模型与思考强度
      → 运行、裁判、复核、报告

### 4.1 论文快照

冻结时至少保存：

- paper_key、标题、作者、来源类型和来源 ID；
- 提取后的完整文本；
- PDF 哈希、文本哈希、字符数和提取器版本；
- 原论文数据库 ID（允许论文之后被删除，但快照仍然有效）；
- Prompt profile 快照和题库校验和。

题库使用冻结文本运行，避免缓存清理、论文版本更新或 PDF 重新解析导致候选模型看到不同输入。

### 4.2 题目与 rubric

每个题目保存：

- 轨道、论文、题目编号和题型；
- 参考答案及可接受的答案变体；
- 一个或多个原文证据片段；
- 逐项评分条件、条件权重和关键错误标记；
- 是否要求拒答或指出错误前提；
- 出题模型原始结果、人工修改记录、审核人和审核时间。

证据片段必须能够在冻结文本中精确匹配。只依赖图片或无法追溯到正文的题目必须驳回。

深度阅读默认将 Q1–Q6 拆成多个叶子条件。Q3 方法和 Q4 实验通常权重最高；Q6 总结不能因为措辞流畅而替代前面的问题。具体权重在草稿审核阶段确定并随版本冻结。

交流题目除了事实条件，还要有：

- 是否正确承接前一轮；
- 是否纠正错误前提；
- 是否区分论文明确结论与合理推测；
- 是否在无法确定时说明边界，而不是编造细节。

## 5. 版本和生命周期

版本格式：

    pprb-<subset>-YYYY.MM.DD-rN

示例：

    pprb-pilot-2026.08.04-r1
    pprb-core-2026.09.01-r1

状态：

- draft：可选择论文、修改 Prompt 快照和生成题目；
- review：题目已生成，等待逐题人工确认；
- frozen：不可变，可用于运行和复现；
- retired：不再作为默认题库，但历史运行仍可查看。

以下任一变化必须新建版本：

- 论文或 PDF 版本变化；
- 全文快照或抽取器版本变化；
- 生产 Prompt 变化；
- 题目、参考答案、证据或 rubric 变化。

裁判模型、裁判 Prompt 和裁判规则使用独立的 scoring_revision。更换裁判可以重新评分已有候选输出，但不得覆盖旧裁判结果。

## 6. 模型配置与思考强度

候选模型不是简单的模型名称，而是一个完整配置快照：

- provider_key、供应商名称和模型名称；
- is_thinking；
- 请求的 thinking_effort；
- 实际发送的 reasoning/thinking 参数；
- 输出 token 上限、temperature 开关和值；
- 配置哈希、运行时间和代码版本。

所有供应商连接复用现有设置，不在 benchmark 中保存 API Key。

不同供应商的思考强度不能直接视为同一尺度：

- OpenAI reasoning 通常可区分 low/medium/high；
- Qwen 类协议可映射为不同 thinking budget；
- 某些 DeepSeek legacy reasoner 不接受可比较的强度参数；
- 不同供应商的 high 不代表相同的推理 token 预算。

运行前应计算实际请求参数。如果两个候选强度最终生成相同请求参数，界面应提示“不具备可观测差异”，避免把同一个配置重复排名。

默认使用每个轨道统一的输出上限。如果用户允许候选使用不同上限，报告必须标记为“非等预算比较”。

## 7. 评分方案

### 7.1 单题评分

每个 rubric 条件只能返回：

    met = 1
    partial = 0.5
    unmet = 0

单题分数为条件加权平均。严重捏造论文方法、数字或实验结论时，该题最高限制为 60 分；同时单独记录 hallucination_critical。

格式完整性属于正式评分的一部分：深度阅读缺失 Q、交流空回答或无法解析的结果，不应被裁判用流畅文字补救。

### 7.2 聚合

    论文分数 = 该论文所有题目的加权平均
    轨道分数 = 所有论文分数的等权宏平均

论文之间等权，避免某篇论文题目更多而主导总分。

报告至少包含：

- 深度阅读榜；
- 论文交流榜；
- 各论文、各题型和各 rubric 切片；
- 关键幻觉、拒答、缺题和上下文不一致次数；
- 输入/输出/缓存 token、延迟、重试、续写和估算费用。

不把质量、成本和延迟揉成一个没有依据的总分，而是展示质量与成本/速度的效率前沿。

### 7.3 LLM 裁判

- 主裁判评分全部输出；
- 第二裁判对每个轨道、每个候选至少抽取 10%，并覆盖低置信度、严重幻觉、格式冲突和同家族候选；
- 主裁判与候选同家族时，报告显示偏置风险；可要求第二裁判作为最终裁判；
- 两裁判不一致时进入人工确认；人工结果优先，但原始判断保留；
- pilot 中通过人工结果计算逐条件一致率和分数误差；裁判未校准时正式报告显示警告。

裁判 Prompt 必须要求“按 rubric 条件判断”，不能按回答长度、文采或总体印象打分。裁判只能看到参考答案、证据、rubric 和候选输出，候选模型不能看到参考答案。

## 8. 成本与重复运行

被测调用量估算：

    候选调用数 = 论文数 × (1 次深度阅读 + 3 次交流) × 重复次数

因此：

- 1 篇 pilot：每个同时评测两条轨道的候选约 4 次被测调用；
- 8 篇正式题库：每个候选约 32 次被测调用；
- 裁判按“每篇论文、每条轨道”批量评分，避免每个叶子条件都单独调用。

这里的数量是未复用槽位的名义调用量，不是可以绕过硬预算的“估算值”。运行创建前按
实际候选配置和槽位计算最低需求；`benchmark_runs.candidate_calls_made` 在每次候选 API
尝试前持久化、原子递增，进程中断或恢复都不清零。深度阅读续写以及候选网络/timeout、429、
5xx 临时错误的额外尝试都各占一次候选调用预算；每个候选请求最多额外重试两次。裁判和复核
裁判调用不占该预算。

运行前必须展示：

- 正常调用数和最坏调用数；
- 输出 token 上限；
- 可能的续写/重试次数；
- 可选的价格快照和估算费用。

用户可设置最大调用数或最大估算费用，超过上限时禁止启动。

`max_calls` 若已设置，启动时必须能容纳所有未复用槽位；运行中耗尽预算会暂停/中断，恢复时
只能严格提高上限，不能用原上限静默继续。相同 suite checksum、`RUNNER_VERSION`、候选
`config_hash` 和（论文、轨道、重复、轮次）槽位的已完成响应可以精确复用，复用输出不增加
目标运行的调用计数；`retry_failed` 或未完成响应永不复用。只更换裁判时使用独立
`scoring_revision` 只重判已保存输出，保留旧判定并在成功后切换 active revision。

默认重复 1 次，允许配置 1–5 次。相同题库、Prompt、候选配置和重复槽位可以复用已有输出；只更换裁判时只重判，不重跑候选。

错误分类：

- 网络、429、5xx、临时供应商错误：最多重试两次，仍失败则标记基础设施失败，不把候选记为 0 分；
- 上下文超限、输出截断、非法格式、拒答或事实错误：属于候选配置/模型能力结果，进入正式成绩并记录原因；
- 题库全文缺失或证据校验失败：题库无效，阻止运行。

## 9. 统计解释和主要风险

### 9.1 样本量

1 篇论文只能验证管线，不能进行可靠排名。正式比较建议至少 8 篇，并尽量覆盖不同论文长度、方法类型、实验密度和熟悉度。

8 篇以下只报告描述性结果；达到 8 篇后按论文聚类 bootstrap 给出 95% 区间。重复 1 次时，区间主要反映论文采样差异，不能充分反映模型随机性。

### 9.2 污染和模型漂移

私有题目降低了直接题目泄漏，但论文本身可能已在训练数据中。问题应优先测试具体正文、跨章节关系、实验细节和错误前提。

供应商模型别名可能静默升级，因此必须保存模型名称、运行时间、请求配置、响应 usage 和代码版本；长期比较时标记“供应商别名可能漂移”。

### 9.3 PDF 和上下文

v1 只评估冻结的文本输入。PDF 解析器是题库冻结前的质量门，不把解析失败混入模型分数。未来如果要测图表或多模态能力，应新增独立轨道，不能把视觉题混入文本总分。

### 9.4 用户主观偏好

数值分数不能完全代表“我是否喜欢这个模型的交流风格”。正式报告之外，应保留一个可选的 finalist 定性复核区，用于记录表达风格、中文自然度、解释节奏和研究启发性，但不修改正式分数。

## 10. 后续实现蓝图

### 10.1 深模块 interface

新增 source/benchmark/，对 Web/CLI 调用方只暴露少量 interface：

    create_draft(subset_name, paper_keys)
    generate_cases(suite_id, background=False)
    submit_generate_cases(suite_id)  # 后台任务，返回 task_id
    review_case(case_id, decision, note="")
    edit_case(case_id, fields, decision=None, note="")
    freeze_suite(suite_id)
    start_run(suite_id, candidates, repeats=1, max_calls=None)
    submit_start_run(suite_id, candidates, repeats=1, max_calls=None)
    resume_run(run_id, max_calls=None)
    submit_resume_run(run_id, max_calls=None)
    rejudge_run(run_id)
    submit_rejudge_run(run_id)
    get_report(run_id)

同步函数保留给 CLI/兼容脚本；Web 入口使用 `submit_*`，由单 worker 后台任务执行并返回
任务/运行标识。PDF 快照、证据匹配、调用重试、模型配置解析、评分聚合和报告生成都隐藏在
该模块内部。外部调用方不应直接操作 benchmark SQL 或拼接裁判 Prompt；只读列表、运行中断
标记和题目/评分 revision 也通过 `source.benchmark` 公共接口完成。

### 10.2 运行时配置

新增三个任务级路由：

- benchmark_author：生成参考答案、证据和 rubric；
- benchmark_judge：主裁判；
- benchmark_judge_review：第二裁判/复核裁判。

它们复用现有供应商、Prompt profile、代理、token 账本和 OpenAI 客户端创建逻辑。

### 10.3 数据库对象

当前连续迁移已落地 schema v7，包含以下逻辑对象：

- benchmark_suites：版本、状态、Prompt 快照、校验和；
- benchmark_suite_papers：论文快照、全文、哈希和提取信息；
- benchmark_cases：题目、轨道、参考答案、证据和 rubric；
- benchmark_runs：`queued`/`running`/`interrupted` 等运行状态、重复次数、裁判版本、
  `active_scoring_revision` 和候选调用预算/计数；
- benchmark_candidates：候选配置快照；
- benchmark_responses：原始输出、解析结果、usage、延迟、`retry_count`、`error_json` 和
  `reused_from_response_id`；失败或未完成响应不能作为复用源；
- benchmark_judgments：主裁判、复核裁判和人工覆盖结果，含 actor 快照；
- benchmark_scoring_revisions：评分规则/路由版本及 active 切换；
- benchmark_case_revisions：题目编辑与审核审计。

冻结数据必须不可变；运行和裁判结果必须可追溯到 suite checksum、candidate config hash、
scoring revision 和 `runner_version`。新运行固定保存 `pprb-runner-v7`，历史空版本保持原样。

### 10.4 Web 管理流程

新增管理员保护的 /benchmark 页面和对应 API，流程为：

    选论文 → 预检全文 → 生成题目（202/task_id）→ 逐题审核/编辑 → 冻结版本
    → 选择候选/思考强度 → 预算确认 → 排队运行（202/task_id/run_id）
    → 裁判/复核 → 查看分榜与逐题报告

生成、运行、恢复和重判均由单进程内单 worker 顺序执行。运行应持久化并可恢复；启动时将
遗留的 `queued`/`running` benchmark run 标记为 `interrupted`，由人工提交恢复，且不得丢弃
已经完成的候选输出。重判只消费已有响应，不增加候选调用量；主/复核条件冲突的题目在人工
覆盖前不计入榜单聚合。

## 11. 实施阶段与验收

### 阶段 A：pilot

- **状态：已完成。**
- 支持 1 篇论文；
- 支持两条轨道、默认重复 1 次；
- 支持逐题审核和冻结；
- 支持假模型 adapter 的自动化测试；
- 报告明确标记“pilot，不构成可靠排名”。

### 阶段 B：正式私人题库

- **状态：v7 核心闭环已实现。**
- 支持用户任意设置论文数量，默认建议 8 篇；
- 已增加预算预估、持久候选调用预算、运行恢复、精确输出复用和裁判复核；
- 已支持按论文聚合、token/延迟/续写/失败切片；按论文聚类 bootstrap 区间仍属于后续统计增强。

### 阶段 C：可选增强

- 图表和公式多模态轨道；
- 决赛候选自动重复 3 次；
- pairwise finalist 比较；
- 可选跨论文检索和文献综合轨道。

验收至少包括：冻结不可编辑、证据精确匹配、缺题计分、严重幻觉限制、思考参数去重、预算拦截、运行恢复、只重判不重跑、管理员鉴权和密钥脱敏。
